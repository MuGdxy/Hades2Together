# 架构

四人在同一局游戏里打同一批怪物，共用一份敌人血量。每名玩家各用一个客户端进程采集自己的游戏输入并提交给权威。权威统一分配席位，把经过检查的输入交给对应的权威角色，并向客户端广播裁决及完整快照。正式运行时权威是哈迪斯 2 进程。

## 已经定下的决定

战斗、敌人、弹道和房间生成都留在游戏自己的函数里。我们决定谁在队伍里、这下攻击算谁的、一个人倒下之后跑是否继续、祝福分给谁。真正扣血的是权威进程上的原版逻辑。

权威进程有两种启动方式，代码相同：

| 角色 | 含义 |
| --- | --- |
| `serve+play` | 这台机器是权威，同时自己占 1 号席。这是主机玩家。 |
| `serve` | 这台机器是权威，本机玩家席为 0。这是专用服务器。 |
| `play` | 独立客户端进程读取自己的玩家输入、发送操作并按快照呈现。 |

`serve` 仍然要启动 `Hades2.exe`，并创建窗口和 D3D12 设备。没有显卡的机器不能当权威。窗口不在前台时游戏会停止模拟；让它在后台继续跑是后面的 `SetFocusTick`，放在 hack 接口里。

客人进程不跑遭遇、不掷怪物、不裁定命中。命中以权威快照为准。

## 一条数据怎么走

```
客人输入
  -> net（Input 意图）
  -> authority 按连接分配的席位验证输入并指定 tick
  -> authority.step
  -> gameplay 产出命令
  -> hack 在权威进程里调用游戏
  -> hack.ReadActors
  -> net（Snapshot / Event）
  -> 客人 hack.ApplySnapshot
```

`gameplay` 只看见事件和命令。它不读 `CurrentRun`，不包游戏函数。

网络席位属于权威会话。原版脚本使用单个 `CurrentRun.Hero`，此前调查记录了本地玩家数组长度为 2。把四个网络席位映射到接受原生输入的权威角色，仍是 `src/hack/game.lua` 的引擎适配问题。需要当前英雄上下文的调用由适配层处理。见 [当前卡点](blockers.md)。

每次同步发送同一个权威 tick 的完整状态，包括该范围内的全部英雄及敌人记录。客户端用更新的快照整体替换视图，快照里缺席的对象随即消失；重新连接收到一份快照即可重建视图。角色的动作、阶段及动作实例标识由引擎在能读取时随角色状态提供。呈现端应保留同一动作实例的动画进度。玩家按键是输入意图，裁决事件供通知使用。

## 玩家输入和游戏接口

客户端将本地玩家动作或摇杆状态编码为 `Input`。权威和本地 CLI 回放通过 `Engine.PushInput` 提交玩家操作。原生接口的解析和参数转换集中在 `src/hack/game.lua`。输入应走游戏用于实际玩家的通道，由游戏执行输入屏蔽、状态检查、移动、转向、碰撞和动画。遇到当前游戏接口无法提交的输入或席位，返回明确的错误。

测试房间启动等没有玩家输入入口的开发操作，可以通过 `hack` 调用已有的原生操作，遵守该操作要求的状态和存档限制。演出移动可以在屏蔽玩家输入时运行。它、直接写坐标和指定动画都不作为玩家输入回放。测试使用的 `hack/fake.lua` 只提供离线替身。

## 席位

最多 4 个席位。权威按连接确定输入的席位，拒绝冒用席位和重复序号。席位跟玩家名字走，断线后仍保留，同名可在旧连接关闭后回到原席。第 5 个人被拒绝。本机 TCP 验证以名字恢复席位，身份认证留给后续的对外传输。

## 本机环境

Steam 版装在：

`C:\Program Files (x86)\Steam\steamapps\common\Hades II\`

`Ship\Hades2.exe` 是带包装的发布目录，`Release\Hades2.exe` 是旁边的另一份可执行文件。社区加载器 Hell2Modding 按惯例放在 `Ship` 里，文件名是 `d3d12.dll`。

开发机的 `Ship` 目录放着 Hell2Modding 的 `d3d12.dll`。插件在 `Ship\ReturnOfModding\plugins`，其中 `MuGdxy-Hades2Together` 链接到本仓库的 `src`。删掉 `d3d12.dll` 就回到原版。
